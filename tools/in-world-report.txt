OptiLithium in-world verification
===============================

Produced by tools/in-world.ps1 on 2026-09-22, one release at a time, with the jars built from this revision
(`tools/build-all.ps1` keeps one jar per release). Every number below comes from a log written by the run that
produced it - the script deletes the game directory first and verifies the delete, because a number read from a
stale log is worse than no number.

What one run does: launch a real client with OptiFine + Lithium + this mod, quick-play into a copy of a world, and
then read only the files that run wrote. "prepared / failed" is the pipeline's own line
`Prepared N patched classes (S skipped, F failed)`; F must be 0. **programs** counts `Program loaded:` lines, and
54 is 27 unique shader programs counted from both the stdout log and latest.log.

Every release that can be launched reaches a loaded world with the shader pack compiled: 15 of 16, each with 0
failed patched classes and 0 crash reports. The one that does not is 1.21, and it is blocked by Lithium:

* **1.21** is blocked by Lithium, not by us. Lithium's only 1.21-family build is `mc1.21.1`, and on a 1.21 client
  its `HopperBlockEntityMixin` cannot find what it injects into:

  ```
  Mixin apply for mod lithium failed lithium.mixins.json:block.hopper.HopperBlockEntityMixin
  Critical injection failure: @Inject annotation on invalidateOnSetCachedState could not find any targets
  matching 'method_31664(Lnet/minecraft/class_2680;)V' in net/minecraft/class_2614
  ```

  `class_2614` is `HopperBlockEntity`, which **OptiFine does not patch at all** - verified by searching
  `.optilithium/<version>/Optifine.classes.gz`, where it is absent - so this class never passes through this
  mod's pipeline and there is nothing here to repair. It is a 1.21.1 jar being applied to a 1.21 client, and the
  method it wants was removed between the two. OptiLithium + OptiFine alone reach the title screen on 1.21.

* **26.1.2** never opens a world, and neither does the game without us: **vanilla Fabric 26.1.2 with no mods at
  all ignores `--quickPlaySingleplayer` and sits at the title screen**. The mod reaches the title screen with the
  shader pack loaded (567 patched classes, 0 failed) and no crash. A thread dump taken while it waits shows the
  render thread parked in `Minecraft.renderFrame` -> `FramerateLimiter.limitDisplayFPS`, i.e. the ordinary game
  loop with no integrated server, which is what the title screen looks like from a stack.

The `thread errors` column counts `[Server thread/ERROR]` and `[Render thread/ERROR]` lines that are not rig
noise. Rig noise is subtracted, not ignored: `Failed to verify authentication` (the rig launches with
`--accessToken 0`) and `Failed to load random sequence ...` (the rig hands an older release a world written by a
newer one) are properties of the harness, and the older releases log ten such lines between them.

Two releases report GL-level errors that are OptiFine's shader code talking to the driver, not a failure:
`[Shaders] OpenGL error: 1282 (Invalid operation), program: gbuffers_*, at: alphaTestRef` on 1.21.6 and 1.21.7,
and the same family on 1.20.2. The world loads, all 54 programs compile, and nothing is dropped.

1.21.9 used to be a gap, and the cause is worth recording because every plausible explanation was wrong:

* it was not the pack, the config file or the pack directory. Selecting OptiFine's own built-in pack
  (`shaderPack=(debug)`) failed the same way; `tools/ShaderConfigProbe.java` reads `optionsshaders.txt` the way
  OptiFine does and gets the name correctly; and a run with the pack unpacked into a *folder* - so that
  OptiFine's `isDirectory()` branch was taken instead of its zip branch - still failed;
* a probe injected into OptiFine's own `Shaders` showed `currentShaderName` ending `loadConfig` as
  `ComplementaryReimagined_r5.9.3.zip`, i.e. the name WAS read;
* the cause is in OptiFine's 1.21.9 bytecode: `loadShaderPack` computes the flag and then overwrites it with a
  constant, so no path can leave it true:

  ```
  192: putstatic shaderPackLoaded        # the honest value, computed from getShaderPack(name)
  195: iconst_0
  196: putstatic shaderPackLoaded        # and then, unconditionally, false
  199: getstatic shaderPackLoaded
  202: ifeq 219                          # always taken -> "No shaderpack loaded."
  ```

  1.21.8 and 1.21.10 do not have that second store. `ClearShaderPackLoadedFix` replaces it with a `pop` - a
  same-size, stack-neutral substitution - and 1.21.9 now loads the pack and compiles the same 54 programs.

How the shared defects behind these numbers were found
------------------------------------------------------

The pipeline's own report line is not enough to trust, and four defects hid behind a healthy-looking
`Prepared N patched classes (0 skipped, 0 failed)`:

* a `NoSuchMethodError` on `BlockEntity.getCapabilities` appeared ~200 times per world load and dropped each
  block entity's NBT (fixed by neutralising the null-guarded calls);
* OptiFine's `multiTex` field was never initialised, so the first dynamic texture ended the client with
  `NullPointerException: Cannot read field "norm" because "multiTex" is null` on 1.21.6 and newer (fixed by
  allocating the id on first use and initialising the field in every constructor);
* the fixer for that field was registered under a name that never matched, so it did not run at all while the
  pipeline reported success - and, once it did run, a `getNext()` walk inside it hung the client at 100% of one
  core for eight minutes with no crash, no error and `prepared=-`;
* OptiFine's 1.21.9 shader class was dropped by the pipeline instead of being patched, because recomputing the
  frames of a class whose frames were already valid failed on an unrelated method of it - an all-or-nothing
  failure that made a correct fixer look like a fixer that had not run.


Each of those is documented at its source: `docs/BLOCKENTITY_CONFLICT.md` and the class comment on
`InitMultiTexIdFix`.
